Quick answer: Enter a password and plaintext to create an AES-256-GCM ciphertext packet, or paste a compatible packet and use the same password to decrypt it. The encryption and decryption operations run locally with the browser Web Crypto API.

Plain text can be read by anyone who gains access to the message in transit or at rest. Encryption makes the content unreadable without the password, while operational security still depends on how the password and ciphertext are exchanged.

AES-256 Text Encryption Explained

How does AES-GCM encrypt text with a password?

AES-CBC provides confidentiality but does not authenticate ciphertext on its own; secure CBC-based designs pair it with a message authentication code. AES-GCM combines encryption and authentication in one operation.

AES-GCM (Galois/Counter Mode) produces an authentication tag alongside the ciphertext. With the correct password, decryption rejects altered packets instead of returning silently modified plaintext. It does not prevent interception, protect an exposed password, or secure a compromised endpoint.

How does PBKDF2 turn a password into an AES key?

The tool uses PBKDF2 (Password-Based Key Derivation Function 2) with HMAC-SHA-256 to derive an encryption key from the password.

New packets apply 100,000 iterations with a random salt. This adds work to every password guess, but it does not make guessing ineffective; use a long, unique password and exchange it separately from the ciphertext.

What do the salt, IV, and AES-GCM ciphertext packet contain?

To execute AES-GCM securely, two unique random sequences are required: a 16-byte Salt (for key derivation) and a 12-byte Initialization Vector (IV) (to ensure two identical plaintexts generate completely different ciphertexts).

New packets bundle those values with the iteration count in this versioned format: v1.<ITERATIONS>.<SALT_BASE64>.<IV_BASE64>.<CIPHERTEXT_BASE64>. For backward compatibility, the decryptor also accepts the earlier three-part salt, IV, and ciphertext format.

[ LOCAL PROCESSING AND OPERATIONAL LIMITS ]

This page does not submit the plaintext or password to a CalAudit server. The browser performs the cryptographic operations with the Web Crypto API, and you decide where to store or send the resulting packet.

Local processing is not the same as complete endpoint security. Browser extensions, clipboard history, malware, screenshots, backups, and a weak or reused password can still expose data. Use a strong unique password and share it through a channel separate from the ciphertext.

Frequently Asked Questions

▶ How do I encrypt text with a password?
Enter a strong password and plaintext, then choose Encrypt. The browser derives a 256-bit AES key with PBKDF2-HMAC-SHA-256 and creates an authenticated AES-GCM ciphertext packet locally.
▶ Can I decrypt AES-256 text with this tool?
Yes, if the ciphertext is a compatible CalAudit AES-GCM packet and you have the correct password. Paste the packet, enter the password, and choose Decrypt.
▶ Is this AES text encryptor free and private?
The tool is free and performs the cryptographic operation in the browser. It does not submit the entered plaintext or password to a CalAudit processing endpoint, but device, browser-extension, clipboard, and password-handling risks still apply.
▶ What does AES-GCM provide?
AES-GCM encrypts the message and authenticates the ciphertext. Decryption fails if the ciphertext, IV, or authentication tag is altered. It does not prevent interception or protect a compromised device.
▶ Does CalAudit upload my text or password?
This page performs key derivation, encryption, and decryption with the browser Web Crypto API and does not submit the entered plaintext or password to a CalAudit processing endpoint.
